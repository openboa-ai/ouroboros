# C1a-01 process verification

## Required coverage

Qualify the actual implementation and its exact built artifacts against the three process roots below. The [case inventory](acceptance-cases.json) contains all 108 required bindings and 14 controls that refine those bindings. Each required control runs with its applicable owning binding, fixture and independent expectation. The [fault cut manifest](fault-cuts.json) defines the declared physical write and filesystem boundaries.

| Root | Required evidence | Required outcome |
|---|---|---|
| C1a-01.N01 (AT05) | Two real service processes on the same directory and on aliases, explicit creation and compatible reopen, actual connection settings and typed storage probes | Exactly one owning writer. Contenders produce zero application mutations. A valid ordinary store reopens and same-key history remains retrievable. |
| C1a-01.N02 (AT05) | Actual SIGSTOP, SIGCONT and supervisor-observed termination, child descriptor evidence, every owning transaction's reached fault cuts and stable original keys | A stopped owner keeps its lock. A successor acquires a checked fresh generation. Reopen verifies complete original states, receipts and budgets, and eligible current work proceeds. |
| C1a-01.N03 (AT17 storage) | Actual denied write, bounded ENOSPC, selected SQLite VFS errors, corrupt/unsupported storage and unconfirmed original outcomes | Preserve original objects and logical data. Classify the failure and hold dependent writes. A matched valid store remains recoverable. |

The qualification supervisor owns the synthetic fixtures, process identities, reached barriers and fault schedule. The independent observer establishes the SQL snapshot, process facts, file identity and expected evidence without consuming subject success claims as its oracle. Expected rows, exact bytes and arithmetic come from the declared fixture and typed vectors. Record each negative check alongside a positive with the same prerequisites and the one discriminating input changed.

## Build and case binding

Build the ordinary `company-service` binary and the qualification subject from the same source, lock and shipping core, ownership and schema-validation code. The qualification binary adds the declared synthetic source, test clock and fault instrumentation. Run ordinary create/reopen/ownership positives with the ordinary binary and exercise its fixture rejection. Use the qualification binary for fixture maintenance, failure cuts and source-control tests. Record both executable digests and the feature selection.

The `c1a_process` integration target uses `harness=false`. Provide `cargo test --locked -p company-service --test c1a_process -- --list --json` to discover case IDs, `--case <root/family/member[@cut]>` to select one, and `--manifest <accepted-required-inventory>` for the full set. The accepted inventory is defined by this specification and the reviewed implementation's actual paths. Compare required, discovered, selected and executed sets, including the 14 controls and physical expansions. Missing witnesses, cases, duplicates and unexpected outcomes fail the corresponding requirement.

Seal the actual SQL statement order, trigger/FK/index and VFS operations, syscall sites, control checks and result-confirmation boundaries for each implemented path. Exercise before first write, after each actual write, before COMMIT, at selected COMMIT faults, after COMMIT returns and after confirmation before response. Independently distinguish a truly absent commit from an already committed result whose reply is lost. For a genuinely uncertain cut require verified original-key reconciliation or the explicit unknown outcome.

Bind filesystem cuts to the actual mkdir, parent and lock synchronization, metadata publication, first SQLite operation and child-launch actions. The supervisor signals only its own fixtures and observes the intended stop/death/lock state. It uses an owned disposable storage image of at most 128 MiB for the full-storage test and independently witnesses ENOSPC. Test VFS returns named errors at the selected real calls and supplies additional controlled I/O failures. These faults require the recorded applied event, its actual operation and the original state. Cleanup follows observed process termination and captured evidence.

Before subject recovery, observe the original files using raw non-SQLite metadata and byte reads or an offline disposable copy of the complete file set. The observer opens the original SQLite store only after an independently observed subject recovery cut. Capture the actual bootstrap file classification, engine recovery role and opening order. The qualifying positive interrupts the pinned initial WAL transition at its first main-page write with an attained durable journal header. Capture the cold and synced-header variants and check the raw predicate before SQLite opens. Compare an initialized disposable store with matching creation and allocation identities and a genuine hot rollback journal produced by unsupported legacy-mode drift. For that negative require zero original SQLite opens and identical main, journal and bootstrap metadata bytes and identities. Independently capture ordinary WAL recovery where an early read could create SHM. Begin observer and receipt reads with `BEGIN DEFERRED` and establish the snapshot with the first company read. [SQLite read transactions](https://www.sqlite.org/lang_transaction.html) · [Read-only WAL behavior](https://www.sqlite.org/wal.html#read_only_databases)

## Recovery and authority checks

| Attained condition | Independent expected result |
|---|---|
| First admitted creation and same-actor original replay | One company, generation/state/sequence `1/1/1`, original creation receipt and one complete group. Replay changes no value. |
| Original startup X committed or absent, then successor Y acquired | Preserve original X identity through response loss. With X committed at generation 2 and Y at generation 3, read the original generation-2 receipt. With X absent and Y at generation 2, prove X absent under the verified current store. |
| Creator dies after provisioning directory or lock | The succeeding creator synchronizes all original entries and applicable files under its acquired lock. A failed required sync yields zero initialization writes. The matched positive initializes the original store once. |
| Initial WAL transition interrupted, or a matching initialized store has a hot legacy journal | Only the exact pre-WAL pair permits the bounded recovery read under the lock. Verify empty original allocation and retry the original initialization once. Refuse the initialized store at raw classification and preserve its original files. |
| Living owner suspended and later actually terminated | The stopped owner excludes a contender. A surviving child neither retains nor releases that ownership. The successor and valid current write proceed after actual termination. |
| U1 committed before its reply, then service restarted | F1 remains `alpha` with encoding 1, B1 stays limit 10 / consumed 3, D1 remains unresolved. At `g/r/s=2/3/5`, M is at checkpoint 1 with one charged attempt and the original U1 result. Only the eligible missing step proceeds. |
| U2 charged before a failed application or unknown response | At verified reopen `g/r/s=2/4/6`, retain charge 2 and the original result. A separately eligible last claim can apply with the total at 3. A fourth claim is denied. |
| Replay a claim or completed mutation in a live actor, after reconnect, or after restart | Match original bytes, kind and any original principal. Return historical receipts before live mutation gates. Hold any still-held permit as it was. No extra permit, charge, write or replacement. |
| Read interrupted by another actor commit | Receipt, current view and reported cutoff all come from the same established read snapshot. A fresh read observes the later commit. |
| Reopen with stale, expired or missing time evidence | Enforce both the original deadline and the current anchor horizon with the new actor's independent clock witness. Test the short-horizon branch while the original deadline is still in the future. Withhold on equality, overlap or missing evidence. A fresh sample just within the applicable limit and current guards allows progress. A blocked branch preserves the prior work and allowance. |
| Linked repair at S1 | Each of SUPERSEDE and REPAIR_ADMIT is necessary on its own. With both exact grants, parent and child receipts commit with one current owner, original causes and original budget. Losing the response leads to the same two historical results. |
| Final validation and response loss | Exact S2 and its original fact, duty and allowance records survive. The final receipt and only its declared cause resolution commit together. A separate stop remains effective. |
| Valid FK but rogue operation, extra audit event or substituted migration digest | Full validation refuses writer generation before any application mutation. The valid companion store passes the same inspection and startup. |
| Checked-generation overflow | The shipping checked increment is reached in an actual bounded child with U64_MAX-1 and U64_MAX. It returns U64_MAX for the first and the explicit overflow for the second before writes. Use an invalid sparse store for a separate lineage rejection, with its own assertion. |

Read the exact values, original ownership and ordered histories in [fixture plan](fixture-plan.json). Exercise all [primitive inputs](codec-vectors.json) on the shipping codec and binders. Verify actual constraints and paired valid/invalid paths for schema, PK/FK, uniqueness, exact numbers, byte digests, canonical fields and CAS. A negative case must reach the named guard independently of another rejection that could mask it.

## Required result record

For each actual case and physical child record root, binding, control, reached cut, applied fault, exact source, binary/lock/profile, runtime settings, original request identity, actual source/statement/affected-row evidence, independent before/after snapshot, expected result, observed result and cleanup. Identify which receipts are original history and which observations establish current permission. Record unavailable outcomes explicitly and retain failed attempts. A final pass requires matching outcomes and sufficient independent evidence for every required member and applicable physical child of the same reviewed build. Repository hygiene checks and local schema inspection cover their own assertions. Product process verification starts in `NOT_RUN`.
