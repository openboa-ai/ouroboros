# C1a-01 company store and restart recovery

## Outcome

A company keeps its identity, committed records and outstanding local responsibilities when its service process exits. A successor obtains sole write ownership, verifies the original store and commits a new generation before accepting mutations. An uncertain commit holds dependent work until the original result can be established.

C1a-01 provides the initial storage and transaction boundary for C1b-01 and C2a-01. Its requirements cover durable facts and obligations (R13), separation of trusted storage access from callers (R14), and evidence for the delivered change (R16). C1a-01 has no preceding implementation unit.

## Interfaces and ownership

The storage actor owns the writer connection, directory descriptor and lock descriptor until every dependent connection and callback stops. The trusted caller supplies request identity and its current access context. Commands accept typed fields and fixed handler IDs. Query results contain typed records. Every writer command uses a private actor witness bound to company, store, generation and startup entry.

| Operation | Input and outcome |
|---|---|
| `CreateStore` | Trusted explicit original creation request with the company, store, initial manifest and destination identity. Return its committed `CREATED` result or a classified failure. |
| `OpenStore` | Preallocated original `entry_id`, expected company, store and creation identities, destination identity and supported compiled profile. A new entry returns a confirmed `OPENED` result and, when current checks permit, a local writer witness. |
| `ReadStorageReceipt` | Current authorized read scope, typed receipt kind and exact original key. Return the historical result and any current observations from one verified snapshot. A fully verified missing original key yields `confirmed_absent`. Incomplete evidence yields `unavailable` or `commit_unknown`. |
| `Transact` | Current actor witness, typed operation, original identity, expected versions and sealed statements. Return a confirmed result, explicit conflict, proved no-commit or unresolved storage failure. Each owning handler defines its own receipt and invariants. |
| `AdmitMaintenance`, `ClaimUnit`, `ApplyUnit` | Exact admitted plan, current control and checkpoint. A confirmed fresh claim may issue one volatile permit in the issuing actor. Applying the unit consumes that permit. |
| `ApplyControl`, `ReplaceWithRepair`, `FinalizeMaintenance` | Exact authorized source change, replacement authorized for both operations, or final validation at the current checkpoint. Commit the defined source, receipt, restriction and responsibility changes atomically. |

`already_running`, `conflict`, `unavailable`, `commit_unknown` and `confirmed_absent` describe the operation outcome. `ordinary` and `recovery_only` describe available repository access. A historical result carries its original generation. Current write permission requires the live actor witness and the owning action's current checks.

### Original startup identity

Before starting the service operation, the trusted caller allocates an `entry_id`, normalizes its `open-request` and retains the exact key and request in its own supervised request record outside the process being started. Retain them through loss of that process or its response. The caller supplies the original identity during reconciliation and allocates a fresh entry ID when requesting a successor acquisition. The qualification supervisor records both identities before launching the respective processes.

An `OPENED` row binds `entry_id`, company and `creation_id` to the original creation row. Reconstruct the original normalized open request from those immutable fields, the original store ID and the directory identity in the verified creation intent. Compare all fields on repeat submission. The format uses a caller-provided ID, with UUIDv4 for service-generated IDs. An existing original ID with different content or kind conflicts. The installed compatibility profile and observed generation belong to the result and current admission checks. A receipt remains queryable by its original key after a later acquisition. When the original group cannot be verified, the result stays unavailable. A confirmed original result yields only a historical receipt on replay, and only a fresh, confirmed acquisition can yield a writer witness.

### Request dispatch order

1. Authenticate current access and validate the closed request and its full canonical input. Enter the actor for operations that could mutate.
2. In a verified read transaction, look up the exact original key and check its complete history and scope. A present complete result may be read under current read access. On replay compare the original kind and canonical body, including any original expected versions and generation. Maintenance replay also matches the original stored principal. Return the matching original result before evaluating live mutation guards. A conflicting body or principal yields a conflict within authorized visibility.
3. Close the read transaction. Only a verified absent key can enter the new-operation branch. A mutation rechecks the original key and current guard values inside `BEGIN IMMEDIATE` under the serial actor. The new branch performs live generation, slot, permission, expiry and resource checks. Only a new application may consume a volatile permit.
4. Keep original lookup and live eligibility distinct in the result. Reading a claim leaves any still-held permit as it was. Receipt replay issues no permit. Preserve original normalized bytes and their digest through retry and repair.

A read connection uses `BEGIN DEFERRED` and reads the company generation and record sequence first to establish its SQLite snapshot. Read the original result, its group and the returned current view in that same transaction. Report that cut with the response. The observer uses the same snapshot discipline. Evaluate any current permission asserted by a response using the corresponding current read proof and snapshot. A response whose eligibility cannot be assessed reports the gap explicitly.

## Directory and startup protocol

1. Close admission. For explicit creation, provision a missing directory with `mkdirat` and mode `0700` under a verified retained parent descriptor. Resolve the authorized directory to its canonical local object and retain a directory descriptor opened with `O_DIRECTORY`, `O_CLOEXEC` and `O_NOFOLLOW`. Verify `fstat`, `fstatfs`, device and inode. Use the zero-extended Darwin `dev_t` bit pattern and unsigned inode as U64. Verify the canonical path still names that object before SQLite opens and before writer admission. Use a cooperating local directory and writers with the same lock protocol. Qualification covers concurrent cooperating processes and path aliases on the declared filesystem.
2. Use `openat` on `company.lock` with `O_RDWR`, `O_CLOEXEC` and `O_NOFOLLOW`. Require a single-linked regular file. Explicit creation may use exclusive creation with mode `0600` in the unused namespace. `OpenStore` uses an existing lock and existing allocation. A nonempty store with a missing or invalid lock yields `unavailable`. Acquire `flock(LOCK_EX | LOCK_NB)` and retain the same open description. A contender returns `already_running` before writer admission or generation change. A living stopped process retains its lock.
3. Under current lock ownership, inspect the exact creation metadata, database and SQLite-managed files. Check `openat` and `fstatat` results without following file links. Preserve unfamiliar, unsealed or incompatible files and report the reason. The supported file set contains `creation.intent`, `creation.allocation`, `company.sqlite` and the applicable engine-managed WAL and SHM files. An interrupted initial WAL transition may leave `company.sqlite-journal`. Use the raw discriminator below before any SQLite open when this file is present. Match the original intent and allocation to the store before admitting its sidecars.
4. Before a new or resumed bootstrap writes to SQLite, synchronize the retained canonical parent entry, stable lock file and directory under the acquired lock. Perform these synchronizations even when another attempt provisioned the directory or lock. Revalidate all applicable already published originals and synchronize their exact files and directory entries before proceeding. A missing confirmation on any of these prerequisites keeps initialization unavailable.
5. Bind the original `creation-request` to company, store, initial manifest and directory identity. Write its canonical `CreationIntent` through exclusive `creation.intent.tmp`, verify complete bytes, `fsync` and `F_FULLFSYNC`, publish with `renameatx_np` and `RENAME_EXCL`, then sync the directory. Allocate `company.sqlite` using `openat` with exclusive creation, `O_NOFOLLOW`, `O_CLOEXEC` and mode `0600`. Verify and sync its file identity. Publish `CreationAllocation` through `creation.allocation.tmp` with the same file and directory sequence. Confirm these original publications before SQLite writes. A visible exact publication with an unconfirmed synchronization is revalidated and synchronized under the current owner. A temp-only, torn or mismatched record or an unsealed allocation remains preserved and blocks dependent work.
6. Classify the original allocation and any rollback journal before SQLite opens. Use the fixed SQLite filename and `SQLITE_OPEN_NOFOLLOW` for an admitted open, with the creation flag disabled. Verify directory and file identity across the open. A proved empty original allocation can enter initial WAL negotiation, then the original schema transaction after verified WAL admission. For normal existing stores, inspect using the read-only role and require a supported WAL profile. An unrecognized or unobservable result remains unavailable.
7. Commit the complete initialization or fresh generation group and verify its result. Resolve unknown original keys using verified storage. A compatible occupied maintenance checkpoint exposes `recovery_only` access until its applicable conditions clear. Ordinary access requires compatible schema and current ordinary admission. A restart does not clear any independent restriction.
8. Close every connection and callback before releasing the lock. The qualification child uses `posix_spawn` with `POSIX_SPAWN_CLOEXEC_DEFAULT`, explicit ownership-descriptor closes and a fixed IPC allowlist. Verify that a surviving child retains neither writer ownership nor the ability to unlock the parent. [Apple flock semantics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html)

| Verified startup state | Permitted continuation |
|---|---|
| Unused namespace with explicit original creation request | Establish the stable lock and synchronized original publications, then initialize once. |
| Exact intent with no allocation or unfamiliar artifact | Continue the original request with the same identities after synchronization. |
| Matching allocated file with confirmed absence of initialization | Run the original initialization after provenance and storage checks. |
| Complete original creation or startup already committed | Read its original result. A successor requires a fresh entry ID and its own acquisition. |
| Unrecognized schema, unsupported file identity, torn metadata or unobservable commit | Preserve the original objects and stop the dependent operation with a classified result. |

### Initial WAL transition recovery

Before the first `PRAGMA journal_mode=WAL`, require the synchronized original zero-byte allocation, the default DELETE journal mode and the pinned page size of 4096 bytes. Only this transition can write SQLite pages before WAL admission. The schema, company records and generation first commit in WAL. The scope manifest fixes the exact 4096-byte empty page emitted by the pinned engine during that transition. The admitted phase has no company schema or records.

When `company.sqlite-journal` is present, inspect the original main and journal files under the retained lock using raw bounded `openat`, `fstat` and `pread`. Require the exact trusted original `CreateStore` request, verified original intent and allocation, stable regular single-linked files on the same device, and an absent WAL, SHM and other unexplained sidecars. Bound the main read to 4096 bytes and the journal read to 512. Recheck directory, file identities and sizes before any SQLite open. Permit the following complete pairs.

| Original main file | Complete rollback journal |
|---|---|
| Zero bytes | One 512-byte cold header with bytes 0–11 zero. |
| Zero bytes or exactly one 4096-byte page with the scope manifest's pinned SHA-256 | One 512-byte header whose first eight bytes match the manifest magic and whose big-endian record count at offset 8 is zero. |

For both header forms, offset 12 holds the engine's four-byte nonce. Require big-endian original page count zero at offset 16, sector size 512 at offset 20 and page size 4096 at offset 24. Require every byte from offset 28 through 511 to be zero. These shapes hold a single header and zero page records. A nonempty legacy database, a journal with a prior page image, mixed sidecars, an incomplete header or an unknown shape yields `unavailable` and preserves the original before any SQLite open. [SQLite database and journal format](https://www.sqlite.org/fileformat.html#the_rollback_journal) · [Pinned engine WAL transition](https://raw.githubusercontent.com/sqlite/sqlite/version-3.54.0/src/vdbe.c)

Only a complete recognized pair enters the dedicated engine recovery connection. Open the exact existing file read-write while retaining the lock and keeping application writes closed. Set the qualified recovery settings and run the fixed `get.catalog` query, allowing the engine to process its journal. Close and verify the same main inode with zero bytes and the journal gone, together with the observed empty catalog. Only that proved outcome permits the original WAL transition to be attempted again. Failed or unobservable checks preserve the admission barrier. A completed WAL transition whose journal is gone may proceed through ordinary classification of the original empty WAL store and its actual catalog. [SQLite rollback recovery](https://www.sqlite.org/lockingv3.html#hot_journals)

## Atomic writes and recovery

Within one owning transaction use `BEGIN IMMEDIATE`, current reads and checked predicates, the mutation-group row, the declared domain statements, the audit event, the company compare-and-swap and commit confirmation. Bootstrap creates one company at generation/state/sequence `1/1/1`, migration `0→1`, one `CREATED` receipt and one IDLE slot. A generation-only reopen advances generation and audit sequence and preserves the state revision. If occupied, bind the original slot and an `EXECUTOR_BOUND` receipt to the new generation in that same group. Use a fresh confirmed entry for each new actor. A semantic change advances the state revision once. A representation-only change keeps it. A historical lookup adds no write group.

Classify a known pre-commit rollback only with evidence that COMMIT was not entered and rollback completed. An uncertain result closes write admission. Retain ownership while draining suspect connections and use SQLite transaction state to select safe close or rollback handling. Recover using the verified store and the original key. A complete committed group returns its original result. A fully verified absent group can enter the applicable current operation checks. A partial or conflicting group is an invariant failure. An unobservable result retains the original obligations and the barrier. A statement error or `BUSY` by itself supplies neither absence nor permission to repeat the body.
